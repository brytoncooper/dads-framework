# Workbench invariants

- INV-WORKBENCH-1: Every successful workspace creation has a durable owner relationship; task creation has a durable workspace relationship — enforced by `operations/workspaces.ts`, `operations/tasks.ts`, and `operations/operation-coordinator.ts`.
- INV-WORKBENCH-2: Resources and versioned authorization change sets commit atomically; failed projection remains retryable, and pending changes drain before access decisions and successful mutation responses — enforced by `storage/sqlite-workbench-store.ts`, `storage/workbench-state.ts`, `operations/operation-coordinator.ts`, and `create-workbench.ts`.
- INV-WORKBENCH-3: Task claims never confer access; workspace membership revocation removes inherited task access — enforced by `access.ts` and `operations/tasks.ts`.
- INV-WORKBENCH-4: Collection reads use authorized IDs, including an empty set, and recheck them within the serialized application boundary — enforced by `storage/workbench-store.ts` and `operations/operation-coordinator.ts`.
- INV-WORKBENCH-5: A workspace retains its owner until the workspace is deleted; membership changes cannot remove or transfer ownership — enforced by `operations/members.ts`.
- INV-WORKBENCH-6: Text artifacts contain at most 8192 characters and remain scoped to their task and workspace — enforced by `contracts.ts` and `operations/artifacts-and-activity.ts`.
- INV-WORKBENCH-7: Stored values are parsed on read and before commit, and callers cannot mutate persisted state through returned snapshots — enforced by `storage/memory-workbench-store.ts` and `storage/sqlite-workbench-store.ts`.
- INV-WORKBENCH-8: Large authorization changes remain one durable operation while projection sends at most 500 tuples per adapter call; replay resumes from the unacknowledged operation and drains it before mutation success — enforced by `operations/operation-coordinator.ts` and `operations/workbench-authorization.ts`.
- INV-WORKBENCH-9: A creation attempt is identified by its authenticated subject, operation, parent, and caller-provided requestKey; its normalized payload and created resource ID commit atomically with the resource, activity, and pending authorization change. A matching retry drains pending work, rechecks current access, and returns the same resource without duplicating state; a different payload or deleted original never creates a replacement — enforced by `contracts.ts`, `operations/create-request.ts`, `operations/operation-coordinator.ts`, `operations/workspaces.ts`, `operations/tasks.ts`, and `operations/artifacts-and-activity.ts`.
- INV-WORKBENCH-10: The creation request ledger retains at most 10000 entries, with no expiry or eviction, including after resource deletion; at capacity new creation keys fail with a conflict while existing keys remain replayable subject to current access and resource existence — enforced by `operations/create-request.ts` and `storage/workbench-state.ts`.

The operation coordinator assumes one application process owns the store and authorization mutations. The default Postgres store combines application state and tuples in one serializable transaction; the selectable legacy SQLite path coordinates atomic local storage, not multiple application processes or external authorization writers.

- INV-WORKBENCH-15: The selectable Postgres store locks one namespace state row and projects its exact authorization change sets through `PostgresAuthorizationStore.transaction` before writing the validated application document. A callback or projection failure commits neither the document nor its tuples; this same-store path never persists an authorization outbox entry — enforced by `storage/postgres-workbench-store.ts` and explicit `storage/postgres-workbench-schema.ts` initialization.

## Local-development ownership

- INV-WORKBENCH-11: Only one launcher may own an instance at a time; its OS-backed exclusive lease covers setup, the API lifetime, and cleanup — enforced by `development/local-state.ts` and `development/run-development.ts`.
- INV-WORKBENCH-12: Startup and shutdown may mutate only Docker resources whose exact names and ownership labels match the instance; the default adapter owns only one Postgres container, network, and retained volume, while the legacy SpiceDB services require an explicit Compose profile — enforced by `development/docker-infrastructure.ts` and `development/compose.yaml`.
- INV-WORKBENCH-13: An instance records its backend in private v2 local state. Existing v1 state means the legacy SpiceDB backend; an explicit conflicting adapter is refused rather than reinterpreting retained data. An initialized instance never silently recreates missing application or authorization storage, and only the legacy backend creates or follows the guarded local SQLite path — enforced by `development/local-state.ts`, `development/run-development.ts`, and `development/docker-infrastructure.ts`.
- INV-WORKBENCH-14: A shutdown instruction is sent only after the target proves possession of the private control key, on that same bounded connection; server proofs cannot authorize shutdown by reflection — enforced by `development/control-proof.ts`, `development/control-server.ts`, and `development/request-stop.ts`.

## Retry contract and local limits

For workspace, task, and artifact creation, generate one requestKey per intended creation (for example, crypto.randomUUID()). The key must contain 16–128 ASCII letters, digits, dots, underscores, colons, or hyphens. After a lost response or 503, retry with that same key and payload; do not generate a new key. Equality is checked after contract normalization, so omitted defaults and their explicit values match. Replay returns the current resource, not a cached historical response. A deleted original yields a conflict when its parent scope is still accessible; an inaccessible or deleted parent remains a 404. Keys from one caller or parent do not identify another caller's or parent's attempt.

The fixed 10000-entry, no-expiry ledger is deliberately bounded for this single-process local example, not a general idempotency service. Deleting resources does not reclaim keys or capacity. There is no automatic pruning/reset. Older local snapshots gain an empty ledger on read; creation attempts made before caller keys existed cannot be identified retrospectively.

Other mutations do not promise general request replay. After an uncertain non-create result, refresh state once authorization recovers before deciding whether another change is needed; do not blindly retry a mutation. Relationship recovery itself remains idempotent and durable. The SQLite adapter uses Node's experimental node:sqlite API (Node 22.14 or newer) and is not evidence of production or multi-process readiness.
