# Authorization battery invariants

Rules about the bridge between lifecycle facts and the enforcement graph that must never be false after any committed operation — how a fact reaches SpiceDB, what may write a tuple, and what replay is allowed to do. The `.zed` schema itself is not listed here; it is validated by assertion files in CI.

- INV-AUTHORIZATION-1: Every permission decision goes through the Authorization interface. SpiceDB evaluates its relationship graph. The experimental Postgres backend evaluates the same policy against its authorization relationship table. Domain rows supply facts through the selected write port. They are never queried by a domain or HTTP handler to answer permission questions. — enforced by `../../access/src/runtime/authorization.ts`, `../../access/src/runtime/route-access.ts`, and `../postgres-access/src/postgres-authorization.integration.test.ts`.
- INV-AUTHORIZATION-2: Writers that use the transactional outbox commit the resource row and relationship facts in the same transaction — enforced by `src/lib/access-changes/enqueue.ts`, `src/lib/access-changes/postgres/enqueue.ts`.
- INV-AUTHORIZATION-3: Every still-eligible outbox fact remains projectable and replay-safe — its idempotency key is unique, relationship writes use TOUCH semantics, deleting an absent tuple is a no-op, and conditional settlement reports success only while the worker still owns the claim. A terminal SUPERSEDED fact is intentionally never projected and records both supersededAt and the replacing fact's idempotency key while keeping lastError null — enforced by `src/lib/access-changes/postgres/access-changes.tables.ts`, `../../access/src/runtime/access-changes.ts#outboxKeyForRelationship`, `src/lib/access-changes/postgres/claim.ts`, `src/lib/access-changes/apply.ts`, `src/lib/access-changes/apply.test.ts`
- INV-AUTHORIZATION-4: Only the projector marks a fact PROJECTED — producers can append and enqueue but hold no claim or projected-settlement method, while the explicit single-source replacement producer may only mark an older exact opposite fact SUPERSEDED under a matching live partition lease; inline dispatch delegates to the projector rather than reaching the graph itself — enforced by `src/lib/access-changes/claim.ts`, `src/lib/access-changes/enqueue.ts`, `src/lib/access-changes/postgres/enqueue.ts`, `src/lib/access-changes/apply-after-commit.ts`
- INV-AUTHORIZATION-5: A revocation removes access immediately and durably, and never half-completes — rowless callers use revokeThrough to commit DELETE facts before touching the graph, while lifecycle writers holding the matching partition lease co-commit their state, event, exact DELETE facts, and opposite-fact supersession before calling deleteCommittedRelationshipsSynchronously inside that lease; an outbox failure leaves the graph untouched and fails the operation, while a synchronous graph failure after commit is logged and does not fail because the durable fact guarantees retry. Grants may wait for projection, revocations never do — enforced by `src/lib/access-changes/revoke.ts#revokeAccess`, `src/lib/access-changes/revoke.ts#deleteRelationshipsNow`, `../../access/src/runtime/owner-lock.ts`
- INV-AUTHORIZATION-6: The projector writes the graph, except when write-through revocation deletes a relationship synchronously after committing its outbox fact — enforced by `src/lib/access-changes/revoke.ts`, `src/lib/access-changes/apply.ts`.
- INV-AUTHORIZATION-7: A mutation never receives a database handle — the transaction a fact rides is opened inside a writer adapter, and the outbox seam is typed to the single capability it uses so no caller can reach a wider database surface through it; from 2026-08-03 this is walled rather than merely true, by a detector banning DrizzleHandle (and the stale DrizzleDb spelling) and its underlying NodePgDatabase alias under any mutations/ directory, because the seam's own doc named it "a boundary the compiler cannot protect and a reviewer will not catch twice" and nothing was checking it — enforced by scripts/detect/rules/no-db-handle-in-mutations.mjs, scripts/detect/rules/no-db-handle-in-mutations.test.mjs, `src/lib/access-changes/enqueue.ts#OutboxTx`
- INV-AUTHORIZATION-8: Projecting a fact inline never fails the operation that caused it — the dispatch that runs after a create's transaction commits swallows both an unreachable graph and a failed claim, logs, and returns normally, because the row and its facts are already durable and the projector heals them on replay; a create that answered successfully has committed, whatever the graph did afterwards — enforced by `src/lib/access-changes/apply-after-commit.ts`, `src/lib/access-changes/apply-after-commit.test.ts`
- INV-AUTHORIZATION-9: Replays of the same revocation reuse the same cause. A later revocation of a recreated relationship has a new cause and therefore a new idempotency key — enforced by `src/lib/access-changes/revoke.ts`.
- INV-AUTHORIZATION-10: Lifecycle writers, synchronous revocations, and the projector take the same owner partition lease. Only a writer holding its matching live lease can supersede an older exact opposite fact. Schedule work that would reacquire the lease with `lease.afterRelease` — enforced by `../../access/src/runtime/owner-lock.ts`, `src/lib/access-changes/postgres/owner-lock.ts`, `src/lib/access-changes/postgres/enqueue.ts`, `src/lib/access-changes/apply.ts`, `src/lib/access-changes/owner-lock.test.ts`.
- INV-AUTHORIZATION-11: Enforcement reads (`check`, `checkMany`, `lookupResources`) are at least as fresh as this process's newest trusted relationship write, and fully consistent when the adapter holds no trusted token (before its first write, after an overlapping, failed, or schema write) or when `SPICEDB_CONSISTENCY=fully-consistent`; a caller-supplied token or the request's consistency cookie never weakens them, and configurable display consistency cannot either. Writes from other processes (the migrator, operator CLIs, another task during a rolling deploy) become visible within SpiceDB's revision quantization window; the API refuses to boot as more than one process unless every read is fully consistent (docs/architecture/authorization.md#consistency) — enforced by `src/lib/access/spice-db-authorization.ts#SpiceDbAuthorization`, `src/lib/access/newest-written-token.ts`, `src/lib/access/spice-db-newest-write-consistency.test.ts`, `src/lib/access/spice-db-enforcement-consistency.integration.test.ts`
- INV-AUTHORIZATION-12: Strict access completion succeeds only after independently observing no PENDING or FAILED facts in every explicitly named owner partition; it never drains unrelated partitions, and an explicit retry may reopen only named, unlocked, nonsuperseded FAILED facts under their matching live partition lease. Only the existing projector settles facts as PROJECTED, and lifecycle coordinators invoke completion after releasing all their leases — enforced by `src/lib/access-changes/complete.ts`, `src/lib/access-changes/postgres/completion-status.ts`, `src/lib/access-changes/complete.test.ts`, `src/lib/access-changes/postgres/completion-status.integration.test.ts`
