# Vitest path adapter invariants

- INV-TESTING-VITEST-1: The export is an ordinary Vite plugin named `dads-tsconfig-paths` that runs before Vite's own resolution, so the resolution boundary is inspectable from the config that installs it — enforced by `src/dads-tsconfig-paths.ts#dadsTsconfigPaths`, proven by `src/dads-tsconfig-paths.test.ts` "exposes an inspectable pre-resolution Vite plugin".
- INV-TESTING-VITEST-2: `resolveId` answers with the path the alias resolver found, and with `null` for a specifier the resolver does not own, so the plugin claims no module the resolver could not prove — enforced by `src/dads-tsconfig-paths.ts#dadsTsconfigPaths`, proven by `src/dads-tsconfig-paths.test.ts` "answers resolveId with the resolver's path, and defers what it does not own".
- INV-TESTING-VITEST-3: The plugin is installed from JavaScript configs, so its options are untrusted: anything that is not an object carrying a non-empty `tsconfig` string is refused before a file is read — enforced by `src/dads-tsconfig-paths.ts#requireTsconfigOption` and `#isRecord`, proven by `src/dads-tsconfig-paths.test.ts` "refuses a blank tsconfig option before reading anything".
- INV-TESTING-VITEST-4: This adapter owns no resolution of its own: every alias, probe, and refusal belongs to `@dads-framework/path-aliases`, is read through that package's `nodeFileSystem` provider, and fails while the plugin is being created rather than while a module is resolved — enforced by `src/dads-tsconfig-paths.ts#dadsTsconfigPaths`, proven by `src/dads-tsconfig-paths.test.ts` "fails while the plugin is being created, not while a module is resolved".
